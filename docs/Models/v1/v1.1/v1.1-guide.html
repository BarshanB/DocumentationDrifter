DocumentationDrifter V1

What v1.1 built, what v1.2 adds next, and how it moves from being called by hand to running on every push and pull request.

v1.1 complete · live at documentationdrifter-production.up.railway.app/system · 2026-10-18

At a glance

DocumentationDrifter will warn you when code changes but its documentation doesn't. v1.1 does the first half, and it's finished: it finds which files changed between two commits, and gives the same answers as the other team's service. Judging whether the docs are now wrong is v1.2, next.

What does it do?
Lists the files that changed between two commits of a public GitHub repo
Where does it run?
Railway, in one Docker container
How does it know which commit?
The caller types the repo and commit ID
Can it see the diff?
Yes, per file (not per line)
Does it use GitHub Actions?
Only to test it, not to run it
Does it find outdated docs?
Not yet: v1.2, with an LLM
Does it match the other team?
Yes, apart from a few agreed differences
Part 1 · How V1 works today

1Where it lives

One container on Railway: an API, a connector that runs git, and a folder of saved results.

  • API: answers web requests under /system.
  • Connector: the only part that talks to GitHub, using git.
  • Run files: each result is saved as JSON so it can be fetched again by its ID.
  • Course routes: /system/test/setup and /test/report tell the grader how much of our code a test session ran.
Free-plan limitsThe service sleeps after 5 to 10 idle minutes, so the first request is slow. Saved results are wiped on every restart. Both are fixed in v3.

2How it gets the repo and commit IDs

It doesn't look for them. The caller supplies them in the request.

POST /system/analyze
{
  "repository":  "owner/name",     public GitHub repo
  "commit_id":   "d0d50c5…",       the commit to check
  "base_commit": "05128cd…"        optional: what to compare with
}
  • The clone downloads history only, not file contents, so it's fast.
  • A short ID like d0d50c5 is expanded to all 40 characters.
  • The copy is deleted after every run.
  • Public repos only: V1 has no GitHub login, so a private repo returns REPOSITORY_NOT_FOUND.

3Which two commits it compares

The commit you send (head) against the one just before it, or any earlier commit you name (base).

4What it sees in the diff

Which files changed and how, but not which lines, and it doesn't yet judge the docs.

FieldValuesDecided by
Change typeADDED, MODIFIED, DELETED, RENAMED, TYPE_CHANGED (e.g. a file becomes a symlink)git
CategoryDOCUMENTATION, IMPLEMENTATION, OTHERFile name, first rule wins: *.md, *.rst, *.txt, docs/ → docs; *.py, *.sh, src/, tests/ → code
SkippedUNSUPPORTED_FILE_TYPE (.png, .svg, .ai, .html, .lock, symlinks, submodules), BINARY_FILE, FILE_TOO_LARGE (over 1 MB), NOT_UTF8File type first, then content. A skipped file stays in changes too

Hidden paths (.github/, .gitignore) are left out entirely. issues stays empty until the v1.2 LLM fills it.

5Where GitHub Actions fit today

Our two Actions only test our own code. Nothing tells V1 when someone pushes.

  • ci.yml: runs our tests on every pull request.
  • acceptance.yml: started by hand; runs the 23 labelled cases of our public test repo against the live service, then compares every answer with the other team's. Green on 2026-10-18.
  • The repos being analysed have no Action. That's the gap Part 3 closes.
Part 2 · v1.2: the drift check (next)

6What v1.2 adds

An LLM reads the changed code and the repo's docs, and fills issues with docs that may now be out of date.

  • Same request, same reply shape. Only issues is new; changes must still match the other team exactly.
  • Model: Gemini Flash on the free tier, behind one function. Switching provider is a config change.
  • No mapping file yet: the LLM reads every doc. A doc-to-code map comes in v1.3 or v2.
  • Probabilistic for now: tests check that each finding names a real changed file and doc, not the exact list. The final version is deterministic.
  • People decide: every finding is PENDING_REVIEW; reviewing comes in v3.
Before any v1.2 codeA draft exists in Source/LLM_Shell/llm.py, but it isn't wired in and can't be imported yet. Six questions get settled first: where the check lives, the type of issue_type, the form of finding_id, how over-budget docs are listed, whether the 120 s limit covers the model call, and how tests run without an API key.
Part 3 · From today's flow to the intended Git flow (v3)

7The change

Today a person calls V1. In v3, GitHub calls it automatically on every push and pull request.

TODAY

Someone finds the commit, sends the request and reads the reply. If nobody does, nothing is checked.

INTENDED · v3

An Action in the analysed repo picks the commits, calls V1 and posts the result on the PR. Dashed = not built.

TodayIntended (v3)
Starts an analysisA person or test scriptA GitHub Action, on every push and PR
Picks the commitsThe personThe Action, from the GitHub event
Shows resultsJSON replyOn the pull request, plus JSON
Saved resultsLost on restartKept
Finds outdated docsNoYes (from v1.2), reviewed by a person (v3)
Comparing engineUnchanged: POST /system/analyze → analyze() → git
V1 itself barely changesThe Action is just a new caller sending the same request a person sends today. All the work stays in one function, analyze(), built to be shared by every caller.

8What happens on a push

The Action does the bookkeeping; V1 does the comparing, exactly as today.

It pings /system/health first because the free service may be asleep.

How the Action picks the two commits

EventHeadBase
Pull requestPR's latest commitWhere the PR branched off
Normal pushNewest pushed commitCommit before the push
Force pushNewest pushed commitLast commit both versions share
New branchNewest pushed commitWhere it split from main
Branch deletedSkipped

"Where it branched off" is the merge base. GitHub returns it in one call, so the Action never downloads the code.

9The move, step by step

Five additions, all in v3. V1's core is already in place.

  1. Today: V1 called by handChange detection works and is live; v1.2 adds the drift check before this move.
  2. Add a workflow file to the analysed repoRuns on pushes to main and on pull requests, read-only.
  3. The Action works out base and headUsing the table in section 8.
  4. It calls the same POST /system/analyzeNo change to V1.
  5. The result appears on the PRA summary on the run and a comment on the pull request.
  6. Results survive restartsMove run files to lasting storage; only runs.py changes.

Things to watch

  • Sleeping service: the Action must wake it and wait.
  • Sharing the Action: if our repo stays private, ship a copy-paste workflow or publish from a public repo.
  • Fork pull requests get a read-only token: summary yes, comment no.
  • Webhook: v3 uses the Action only. A webhook calling the same analyze() waits for v4, since a sleeping free service loses its deliveries.
